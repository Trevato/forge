Big Bang in a Box

The forge is the platform. One process, one file of state, real git underneath, runs anywhere. Inside it the atom is a resource contract; apps are compositions of resources, so they stay liquid. Forks follow their upstream, divergence is shown in the artifact, convergence is a proposal the crew prepares. Drop a forge anywhere and go.

What this page is: the decisions taken today, the shape they imply, the two things to build first, the order for the rest, and how it maps to dollars. Evidence came from four read-only researchers (forge and open-platform-ts on disk; follow/diverge UX; sync engines and mobile; hosting runtimes, air-gap and pricing) plus a fifth on proofs and Apple compute.

The atom is the resource, not the app

The forge already hands every scaffolded app identity (signed headers, roles anon/user/admin), SQLite with an integrity check, an MCP server, live events, a terminal, CSP, rate limits and a body cap. What it does not hand out is the thing you build apps from: a clean CRUD-L resource with rules. Today each app writes its own doors, and the audit showed what that costs: three of four terminals granted more than the web page did.

A contract is one declaration. The forge does the rest, and the rest is where reliability and security live. 

roles({                                   // declared, not enumerated in code
  anon:      {},
  user:      { above: "anon" },
  member:    { above: "user",  when: tuple("member", "team") },   // relationship
  author:    { above: "user",  when: row("author").is(me) },      // row attribute
  moderator: { above: "member" },
  admin:     { above: "moderator" },
})

resource("post", {
  fields: { title: text(1, 120), body: markdown(), author: ref("user") },
  can:    { create: "member", read: "anon", update: "author|moderator",
            delete: "admin", list: "anon" },
  sync:   "fanout",                 // server-authoritative; "shared" opts a table into CRDT merge
  events: ["created", "updated", "deleted"],
  limits: { create: "30/h per identity", body: "64KB" },
})

From that the forge generates the table and its migration check, the three doors (HTTP, MCP, terminal) gated by the same rule, the sync endpoint (GET /sync/post?since=, plain HTTP, resumable, authorized per request by the identity already on it), outbox events, quotas, and a test that the doors match. The scaffold's tools become generated MCP tools. Nothing here needs a runtime dependency; the outbox, the identity and SQLite are already in the forge, and the sync endpoint is a few hundred lines in its style.

Roles will grow, so roles are data too. A role is a name, the roles it sits above, and an optional membership rule that is itself a value: a relationship tuple (member of a team, owner of an org, editor of a document) or a row attribute (the author). New roles are new rows in that declaration, never new code, and the evaluator does not change size when the role count goes from six to sixty. Every scope declares its own roles under the floor's: an app adds "moderator", a fork adds "playtester", and each new role must sit below one that already exists, so downstream can only refine. The forge can act as any declared role, which is how the audit probes each one.

Why this is the liquidity you described. A resource can move between apps. A new app can adopt an old app's resources and replace it. Forks diverge at the composition layer, so convergence is mostly automatic and the crew only has to think at true conflicts. Most app traffic is fan-out of server state to many readers, which is replication, not CRDT merge; the CRDT escape hatch (cr-sqlite as a loadable extension) exists for the few tables that need concurrent editing.

Proven contracts. No dependency, and the guarantee still holds. The contract is data, not code: a declared role lattice, finite per scope however large it grows, five verbs, membership rules that are values. A total evaluator over that is a hundred or two lines, and a test that enumerates every declared role × verb × rule outcome against the table is a proof by exhaustion at any role count, the same property Cedar's Lean proofs give its evaluator, at the scale where you do not need Lean to get it. All three doors (HTTP, MCP, terminal) are generated from that one evaluator, so there is nothing else to prove. Because the contract is data, the same declaration and the same exhaustive table port to Swift unchanged; the evaluator is rewritten in an afternoon and proven by the same table. Cedar stays a dev-only oracle if you ever want an external check: export the table to Cedar policies and differential-test the two evaluators in CI. Effect is a different question: typed errors, structured concurrency and schema inference across a codebase, which the forge hand-built as Result, leases and the outbox; adopting it is a rewrite of the idiom of 104k lines for things already present, and it has no Swift. Crew-provable now, narrowly: hand-picked invariants (migration reversibility, one guard function) in Lean 4 inside a check job. 2027 and later: proving generated TypeScript wholesale as a merge gate; no tool does that today. Bend 2 (2026-09-17) merges Kind's proof checker with the HVM runtime, but it proves Bend code, not yours. Accurate claim: "authorization is a finite table, exhaustively verified, enforced identically at every door." Overstated: "the contract is proven."

Policy is the environment

Because the contract is data, the whole platform's policy is one table: every resource's can block, its limits and sync mode, each app's variable scopes, each forge's tiers, quotas and sleep rules, each repo's direction and ceiling. That table is not a queue of decisions. It is the room the crew works in. You decide the room up front, mostly once, and inside it the crew never asks. The same table is what the crew builds to and what you audit, and all three read the same bytes. That is the answer to trusting trust: the audit never reads the code or the docs, it reads the policy and then probes the running system to see whether the system agrees.

Frontloaded, then autonomous

  • Autonomous is the default for every repo. A direction paragraph, a daily ceiling, ship on green, converge on conflict, park after two red tries, replan when the map runs dry. Directions never finish: "squeeze out inefficiency", "find what this engine wants to become", "keep cs-engine getting better" are standing directions, and coming back to find it newer is the product.
  • The walls are the only place a person is asked. Five crossings, and nothing else: loosen a can cell toward anon, add a runtime dependency, raise a ceiling, change a direction, open a new outside surface (a domain, a webhook, a payment). Everything inside the walls is the crew's call. The decider triages a crossing before it reaches you, with the crew's evidence attached, so most arrive as "probably yes".
  • Crossings batch into one cadence. A weekly policy review is a routine that gathers every open crossing into one session. You decide in minutes; the ledger records who and why. Skip a week and nothing waits on you: the wall holds, the proposal parks, and the map routes builders to other ready work. Absence never stops the crew and never loosens anything.
  • Policy has a floor. Your forge's floor cannot be loosened by an app, an org or a guest forge below it; they can only tighten. A fork follows its parent's policy the way it follows code, and an upstream change arrives as a proposal, never a force.
  • Inside the walls, enforcement is mechanical. The brief carries the policy in force, the reviewer's checklist is derived from it, and the check fails on any door that does not match the table. A red audit cell becomes the crew's work automatically; it never becomes your ask.

A forge is a node

"Floating infrastructure" and "my own edge" are the same requirement: any box you can reach becomes capacity, workloads land where there is room, and nothing important lives on only one of them. The forge is the control plane for its own box today (it deploys apps, previews, checks). The step is to let a forge place work on other nodes and host other forges.

join
A node is a box with git, Bun and a tailnet address. It registers with a forge and announces capacity. Adding one is one command.
place
The forge places an app or a guest forge by priority and room, the way the droplet's warden already evicts the least recently used sleeper when space is needed.
sleep
Everything scales to zero after 24 hours idle or on pressure, lowest tier first; essential things never. Firecracker snapshots make a wake feel like a lambda.
isolate
Trust decides the runtime. Your own apps: processes. Friends: processes or microVMs. Strangers: microVMs, always, with CPU, memory, disk and process quotas. A microVM needs KVM, so that tier lives on bare metal (vxrail, a Hetzner box); a droplet runs the cheap tier under gVisor.
keep
One SQLite file per forge streamed to object storage (Litestream), snapshots as a named verb. Longhorn and Rook solve a different problem and are not needed here.
own
Every forge has its own key. A parent forge cannot decrypt a child's secrets, and boot refuses to start if any secret is sealed to more than one recipient. Ported from open-platform-ts, where a CI test already proves it.
share
Forge to forge is origins: mirror, write through, follow. Git is the universal layer; everything above it is a thin adapter, and a forge is just one more origin kind.

"Even if they do something dumb they can't break things or touch my stuff" is four mechanisms, all mechanical: a separate kernel per guest, quotas at the door and in the cgroup, eviction that always takes the lowest tier first, and a key per forge. None of them are policy.

The Following screen

Core is already correct: forks fast-forward on parent push, divergence is detected, a fork proposes back with a pull. It is then thrown away. There is no ahead/behind, no tree, one flash message. This screen is the product, and it is the demo you show someone before you hand them a link.

How a converge run works

  1. git merge-tree --write-tree asks git whether the two tips converge cleanly, without a working tree. Clean means one click, or automatic for a fork in autonomous mode.
  2. A conflict starts a converge run on the fork: the crew merges upstream, keeps the fork's direction paragraph as the tie-breaker, and pushes a proposal branch. This is the existing bringUpToDate path, pointed at a fork's default branch instead of a pull.
  3. The fork's own forge.json check runs on the proposal and the Look renders it. Nothing is shown to a person until it is green. This is the pattern GitHub shipped for Copilot this year: resolve, verify against the tests, then present.
  4. True diversion points become a decision card with fixed choices (keep mine, take theirs, both, ask). The decider already does fixed-choice questions; the card lands in Asks-you, on the phone if it is critical.
  5. Accepting merges the proposal into the fork. Declining parks it with a note. Nothing is ever forced; a follower's own changes are never lost by default.

Rules the screen keeps

  • Sentence first, numbers second. Stale and diverged get different weight.
  • Show it in the artifact: the Look, the preview, the running game. The diff lives under "details".
  • Partial acceptance at a meaningful unit. With compose-first that unit is a resource or a module, never a hunk.
  • Ambient status everywhere a fork appears: repo header, studio app row, forks page.
  • Propagation is Renovate's shape: when you push, every follower gets a proposal, never an update.
  • Lineage is a diagram once there is depth. The map page's layout engine draws it.

Feel at home

  • Environment classification. App variables are one set today, applied to production and every preview alike. Add scope (production, preview, all) and a sensitive flag. Previews can carry their own test keys; sensitive values are write-only, as now.
  • Studio and dev become one. Studio is a single page over the same tables and a cookie. One page model with the studio words on top (tell, working, look, shipped, asks you) and git as disclosure. The cookie goes away.
  • The Claude app is the phone UI, today. The forge exposes one remote MCP server (OAuth, the same identity as the web) with the studio verbs as tools: tell, asks, decide, ship, look, converge. Add it to your Claude account and every phone you own has the forge, with no app to build. Robustness is the whole job: short tool calls that never hold a stream open across the tunnel's cut, idempotent actions keyed the way the API already keys them, and a sleeping forge that wakes on the first call.
  • PWA second. Manifest, service worker, install, push for asks the crew marks critical. Zero store gate, zero second UI. Push waits until the crew's signal is quiet enough that a notification means something.
  • The ten phone quirks as a checklist on a real iPhone: dynamic viewport height, safe areas, 16px inputs, 44px targets, the composer over the keyboard, hover-only affordances, sticky inside scroll containers, back-swipe, horizontal overflow, momentum in nested panes. The Look already screenshots at phone width; make it fail on these.
  • Native shell later, Capacitor around the same pages, when store presence and richer push matter. Apple's on-device model as a free decider for summaries and fixed-choice questions: the on-device Foundation Model (about 3B parameters, 4k context, structured output and typed tool calls) is free and unconditional, but native Swift only, never Safari or a PWA. Private Cloud Compute opened to third parties this June, free only under the Small Business Program and two million first-time downloads, running Apple's models rather than yours. Good for summarizing asks and answering fixed-choice questions on the phone; it cannot run a coding agent. One rule to build in from day one: since November 2025 any app that sends user data to a third-party AI must show an in-app consent prompt, and the crew calling Claude counts.
  • The terminal is already mobile. Blink over SSH survives network drops better than any webview; keep it first-class.

Build order

Each phase has one acceptance test in the spirit of open-platform-ts's single CI loop. Order carries information; dates do not, the crew sets the pace.

  1. Following and converge. A friend's forge shows the relationship at rest; a clean update is one click; a conflicting update becomes a crew proposal with a green check, accepted from a phone.
  2. The contract, the policy, the audit. A scaffolded app declares a resource and gets its three doors generated from one evaluator; the exhaustive table passes; a policy change is a proposal that blocks the work depending on it until decided; the audit screen shows one deliberate mismatch in red the morning after it is planted.
  3. Feel at home. The forge on your Claude account as a connector; variables scoped by environment; one page model; PWA installs and pushes only critical asks; the ten quirks pass on a real device.
  4. Sovereign hosting. A guest forge provisioned by code in seconds with its own key; the negative test proves you cannot read it; a free tenant burning CPU is evicted first and you never notice.
  5. The highway. A resource declared with sync fans out to every client over plain HTTP, authorized per request; a second app adopts that resource and the audit still reads one table.
  6. Money. A stranger signs up, gets a deprioritized free forge, upgrades; the first client platform is absorbed into a forge and billed.
  7. Forge on your desk. The crew runs on a local model behind the same runner; the Spark builds a hello app with no network.

Phase 1 is web-layer work on correct core. Phase 2 is the foundation everything after it reads from. Phase 3 is polish and a connector. Phase 4 is mostly a port plus the runtime tier. Phase 5 builds on 2. Phases 6 and 7 are packaging.

Money

Three numbers, the way every platform does it, and nothing hidden in "agent minutes".

Line Illustrative price What it means
Awake $0.01 per GB-hour of memory while running A 1 GB forge that never sleeps is about $7 a month; one that sleeps 20 hours a day is about $1.
Storage $0.15 per GB-month Repos, app data, snapshots. Off-site copy included.
Crew credits at 1¢, metered per run at cost plus margin The variable cost is priced as the variable cost. This is where GitHub and Vercel both moved in 2026 after flat agent pricing lost money on heavy users.
Free 1 forge, 512 MB, sleeps after 24h idle, lowest priority, a small monthly credit Unlimited people. They understand they come last.
Friend code free tier with friend priority and comped credits Your call, one code, revocable.

The numbers are tunable; the shape is the decision. Self-hosting stays free forever, which is what lets the hosted price stay honest. First revenue does not wait for any of this: a client platform absorbed into a forge is an engagement you can sell now.

Do not build on "bring your own Claude subscription". Anthropic shut that path for a third-party harness this year. Metered API keys or your own credits are the packaging that survives.

What I am not sure about

  • Whether the resource contract's sync should be written in the forge's zero-dependency style or adopted. The closest external fits are Electric (Postgres-bound, acquired by Databricks in August) and Triplit (perfect shape, tiny team). My lean is in-house with Electric's protocol as the reference.
  • MicroVMs need KVM. The droplet cannot host that tier; vxrail and any rented bare metal can. The cheap tier on a droplet is gVisor, a weaker boundary.
  • The Spark is a supervised single-developer sandbox today, not an autonomous crew: memory bandwidth caps dense models hard and the thermal throttle is only partly fixed. Prototype the harness now, ship the product line in 2027.
  • The map page's layout engine and the studio page were both built fast this month; the Following screen will find their edges.
