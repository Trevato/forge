# The Later gate in plain sight (#8700)

The Later gate (`Later gate: …`, read by `core/pillars.ts`) holds work back from the crew. A person is told so where they look:

- **Home** says, per repository you write, `N issues are held behind the Later gate in <repo>, set by <who> <when>` (`web/studio/held.ts`), and the line opens `/:owner/:name/held`.
- **A held issue** says so at its top, with **Lift** (`web/pages/gate.ts`). Lift is `liftHold` (`actions/gate.ts`): the issue stops waiting for the gate, and its `Later` label goes with it. The MCP `lift` tool is the same action.
- **The label and the gate are one thing.** Giving an issue `Later` puts it behind the gate; taking `Later` off lifts it (`followLabel`, called from `setIssueLabels`). The other direction, an edge changing the label, was already `actions/pillars.ts`.
- **The pass over the lot** (`/:owner/:name/held`, MCP `held`, the terminal's held screen) reads titles and bodies, with no model and no run (`core/gate_triage.ts`). Unchosen ideas are dropped, not tracked (Shape Up): every held issue is a candidate to close, grouped by the word its titles share most, unless it is proposed keep or merge (below). Only done and merge start ticked; **unticked stays behind the gate**. An issue that open work waits for says so on its row, because closing it parks that work (`dropped` holds dependents). One button applies the ticked (`applyGateReview`). The form carries a digest of the candidates shown (`reviewDigest`, their sorted numbers and verdicts); if the gate holds other issues when it is applied, it refuses and closes nothing. An agent may read the proposal and never applies it.
- **Closed ones stay findable.** The apply writes the `issue.gate_reviewed` event after each close, and a comment note beside it. The event, not the note, is the marker (`closedByReview`): it is the review's only while it is newer than the issue's last close and reopen, and a comment cannot forge it. Each is listed under "Closed by the review" on the held page and shows **Revive** at its top. Revive (the same `lift` action) lets it out from behind the gate and reopens it as one outcome: the hold is checked first, and a reopen that fails puts the hold back.
- **The terminal** has the same page: `h` on a repository's issues, or "Held by the Later gate" in the palette (`tui/screens/held.ts`). `space` ticks (a keep row shows `[-]` and has no tick), `A` applies the ticked (close or merge), `l` lifts or revives. It reads and acts through the same functions, so a reader is refused in the same words and a private repository is not found; the web hears each write as the close, reopen and unblock events it already follows.

Not done: snoozing an issue until a date or until new activity.

## The pass proposes keep and merge too (#8813)

`core/gate_triage.ts` reads titles and bodies in one pass of word counting: no model call, no cost. Close is the default. An issue that serves a pillar, or that a pillar's open work or a `Bet:` issue names as `#N` (or names it), is proposed **keep**, with the anchor named. A held issue whose title or body is nearly the same as an older held one is proposed **merge**: on apply, its body is appended to the survivor (never replaced), and the duplicate is closed with a note pointing at the survivor. Done and merge start ticked; keep has nothing to tick. The digest covers each verdict, so the apply refuses if the gate changed.

A merge whose survivor is ticked in the same apply is skipped, so the words never land on an issue that closes in the same breath; the duplicate stays open. A bet is found by its `Bet` title among the first 64 such open issues outside the gate; more than that are not read, which is a heuristic until bets (#8713) are a thing of their own. In the terminal, `A` applies and the toast says "Closed or merged N."; a keep row is `[-]` and `space` does nothing on it.
